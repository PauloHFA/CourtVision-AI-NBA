1. Resumo executivo e proposta de valor
O CourtVision AI combina previsão estatística de partidas e recuperação de conhecimento para produzir uma experiência
interativa e explicável. O usuário seleciona duas equipes, define o mando de quadra e uma data de referência, visualiza as
probabilidades previstas e pergunta ao assistente quais evidências sustentam a análise.
O núcleo preditivo aprende por aprendizado supervisionado a partir de resultados passados, aplicando recursos
estatísticos calculados somente com informações disponíveis antes do confronto. O módulo RAG recupera registros,
resumos verificáveis e artefatos de metodologia; o LLM sintetiza a explicação, sem alterar a probabilidade calculada pelo
modelo.
Critério de sucesso do projeto: entregar uma aplicação reproduzível capaz de prever partidas futuras sem
vazamento temporal, responder perguntas com referências verificáveis, exibir incerteza e publicar o código de
forma compatível com os direitos de uso dos dados.
1.1 Perguntas que o sistema responderá
 • “Qual a chance estimada de Boston vencer Denver em casa, usando apenas o histórico até determinada data?”
 • “Quais tendências recentes sustentam a previsão: campanha, descanso ou desempenho em casa/fora?”
 • “Como o modelo se saiu em uma temporada de teste nunca usada no treinamento?”
 • “De onde veio esta estatística? Qual a data de atualização e o jogo original?”
 • Na etapa avançada: “Como um cenário hipotético com jogador indisponível altera a previsão?”
 
1.2 Fora de escopo
 • Aconselhamento de apostas, indicação de retornos financeiros ou garantias de resultado.
 • Estimativas causais do impacto de um jogador sem modelo específico e validação adequada.
 • Treinar um LLM de linguagem do zero; no MVP o LLM é pré-treinado e utilizado com RAG.
 • Distribuir um feed de dados esportivos concorrente à API fornecedora.
 • Dados ao vivo com disponibilidade ou precisão garantidas.

CREATE INDEX idx_games_date ON games(game_date);

7. Ingestão, limpeza e qualidade dos dados
7.1 Processo ETL/ELT
 1. Criar conta e chave de API; validar se o plano inclui as rotas desejadas.
 2. Consultar metadados de equipes e jogos por temporada ou período com paginação por cursor.
 3. Salvar payload bruto em ambiente local e hash do lote, sem incluir chaves de acesso.
 4. Normalizar tipos (datas, inteiros, booleanos e nomes), mapear chaves e deduplicar.
 5. Fazer UPSERT por ID do fornecedor e registrar contagens inseridas/atualizadas.
 6. Auditar completude, conflitos, cobertura por temporada e jogos sem resultado final.
 7. Gerar snapshot lógico versionado, acompanhado de relatório de qualidade.
 
7.2 Tratamento de limites e erros
 • Autenticação ausente/inválida (401/403): interromper, registrar evento e nunca tentar contornar a restrição.
 • HTTP 429: respeitar Retry-After quando existir; caso contrário backoff exponencial com jitter.
 • HTTP 5xx/timeout: repetir com limite e checkpoints; não repetir erros permanentes de parâmetros.
 • Persistir cursor de paginação e avançar somente depois de commit transacional.
 • Implementar limites locais mais conservadores que o teto do plano, com logging de consumo.

Python — acesso paginado, exemplo de esqueleto
import os, time, requests
BASE = "https://api.balldontlie.io/v1"
TOKEN = os.environ["BDL_API_KEY"]
def iter_games(season: int):
    cursor = None
    while True:
        params = {"seasons[]": season, "per_page": 100}
        if cursor is not None:
            params["cursor"] = cursor
        resp = requests.get(f"{BASE}/games",
                            params=params,
                            headers={"Authorization": TOKEN},
                            timeout=30)
        if resp.status_code == 429:
            time.sleep(int(resp.headers.get("Retry-After", "15")))
            continue  # produção: limite de tentativas e jitter
        resp.raise_for_status()
        payload = resp.json()
        for game in payload.get("data", []):
            yield game
        cursor = payload.get("meta", {}).get("next_cursor")
        if cursor is None:
            break
O trecho demonstra integração, não é pipeline pronto: adicionar persistência de checkpoint, retries limitados, throttling,
validação de esquema e logs antes da operação prolongada. Conferir os nomes atuais dos parâmetros na especificação
OpenAPI do fornecedor [F01].
8. Formalização do problema preditivo
8.1 Variável-alvo e universo
Classificação binária: y = 1 se o mandante vencer o jogo finalizado; y = 0 caso contrário. No basquete profissional não há
empate final em partidas concluídas. Na etapa inicial, incluir apenas temporada regular, se o objetivo for uma população
homogênea; playoffs são outro conjunto de avaliação ou um recurso explícito.

8.3 Fórmulas de referência
Taxa de vitória recente: WR(t,k) = vitórias nas últimas k partidas anteriores / quantidade observada (até k).
Saldo médio: PM(t,k) = média de (pontos da equipe − pontos adversários) nos últimos k jogos anteriores.
Desempenho relativo: ΔWR = WR(mandante,k) − WR(visitante,k); analogamente para saldo e descanso.
Recência: usar janela de 5 e 10 jogos; cold start: voltar à média da temporada anterior/estimativa neutra e registrar
indicador de imputação.
8.4 Garantias de não vazamento temporal
 • Ordenar observações por data/hora real do evento e disponibilidade conhecida; só atualizar estatísticas após a partida
 ser finalizada.
• Nunca utilizar placar do confronto a prever, resumo pós-jogo, classificação final da temporada, box score final ou
 notícias posteriores.
• Na inferência histórica, reconstruir features compatíveis com o instante previsto; validar que as_of é anterior ao início
 da partida e registrar limites de horários não disponíveis.
• Não normalizar, imputar, selecionar features ou fazer tuning usando o conjunto de teste; fit apenas no treino.
 • Se houver vários jogos na mesma data sem hora confiável, calcular features a partir de dias anteriores para evitar
 compartilhamento indevido de informação.

10.3 Ciclo de treinamento
 1. Fixar dataset snapshot, escopo de temporadas e política de ausências.
 2. Gerar features pré-jogo em ordem cronológica e gravar versão da engenharia.
 3. Treinar baselines no treino e medir validação walk-forward.
 4. Treinar XGBoost com busca limitada de hiperparâmetros (Optuna opcional).
 5. Calibrar probabilidades em amostra posterior e separada, sem sobreposição com fit.
 6. Selecionar o modelo pelo critério primário pré-registrado (Brier menor com ganhos estáveis).
 7. Congelar modelo, encoder, imputação, calibrador e metadados juntos.
 8. Avaliar UMA vez no teste externo, gerar relatório, erros e limitações.
 9. Promover o artefato se passar gates de qualidade e testes de regressão.

11. RAG: escopo, indexação e funcionamento
11.1 O que será “treinado” no RAG?
O RAG (Retrieval-Augmented Generation) não consiste, por si só, em treinar pesos do LLM. O sistema prepara dados e
documentos, gera embeddings e recupera evidências na consulta. O LLM usa o material recuperado para responder. Um
eventual ajuste fino de LLM é outro experimento, fora do MVP.
As estatísticas tabulares são tratadas com consultas SQL aprovadas e parametrizadas, pois embeddings podem perder
exatidão de números. Trechos textuais sobre partidas, tendências, glossário e metodologia são indexados para busca
semântica. O sistema une essas fontes.

11.3 Processo de indexação
 1. Gerar registros textuais a partir de fatos conferidos e anexar proveniência por documento.
 2. Definir unidade de chunking por partida ou bloco de 150–450 tokens, evitando cortar campos-chave.
 3. Armazenar document_id, source_ref, game_date, available_at, embedding_model e checksum.
 4. Gerar vetores usando modelo de embeddings local (ex.: família multilíngue compatível); fixar a versão.
 5. Usar busca exata no protótipo; adicionar HNSW no crescimento ou quando latência justificar.
 6. Implementar recuperação híbrida: filtro temporal + SQL estruturado + similaridade de texto; re-ranking opcional.
 7. Desabilitar documento posterior a as_of em perguntas sobre previsão histórica.

13. Simulador interativo: regras e limites
13.1 Simulação do MVP — seleção de equipes
Usuário define mandante, visitante e data as_of. O backend deriva os últimos jogos conhecidos até a data, produz as
probabilidades e identifica fatores associados à previsão. Não se trata de simular jogada por jogada ou placar exato; o MVP
prediz a chance de vitória de cada equipe.
13.2 Extensão — cenários de elenco
Um botão como “Jogador X indisponível” não deve existir no MVP gratuito como estimativa quantitativa válida: somente
nomes de jogadores e placares não permitem inferir o efeito de sua ausência.
Para a extensão, construir features com projeção pré-jogo de minutos, estatísticas rolling por atleta, roster conhecido
antes da partida, indicador de disponibilidade e força agregada por escalação. Treinar novo modelo e avaliar ganho fora de
amostra. Intervenções na disponibilidade devem mostrar “cenário hipotético associativo”, nunca “impacto causal
garantido”.

Los Angeles (mandante) x Boston (visitante) — probabilidade ilustrativa: 54% x 46%. Interface destaca forma
recente, descanso e mando de quadra, registra versão do modelo e oferece botão “Ver evidências”. Esses
números são exemplos visuais, não uma previsão real.

obrigatórios de sua matriz foram comprovados com evidência vinculada ao commit.

Apêndice C. Critérios para adicionar dados de jogadores
O módulo de jogadores tem uma decisão separada de entrada em produção. A rota /v1/stats consta no plano All-Star e
superior [F01]. Para uma simulação de ausência, porém, não basta obter box scores: é necessário reconstruir o que se
sabia antes da partida.
 • Fonte: acesso legal ao histórico individual e documentação de disponibilidade/lineup, quando houver.
 • Temporalidade: features de jogador somente a partir das partidas anteriores à consulta, roster/lesão conhecidos no
 corte.
• Disponibilidade: não tratar estatística ausente ou minutos zero como prova de ausência, DNP ou lesão; o provedor
 explicita essa limitação [F01].
• Validação: novo modelo deve apresentar ganhos externos em métricas registradas e estabilidade entre temporadas.
 • Interface: mostrar cenário hipotético e intervalo de incerteza, sem causalidade implícita.
 • Governança: revisar custos, direitos, cobertura, fonte de sinais pré-jogo e regras de reprodutibilidade antes do merge.
 
Prioridade recomendada: não iniciar a extensão de jogadores antes de completar AC-01 a AC-13. Assim, todo o
projeto continua demonstrável e publicável com o plano gratuito, enquanto a parte avançada fica como trilha
opcional e tecnicamente fundamentada.

D.2 Consulta temporal para histórico de uma equipe
 SQL PostgreSQL — 10 partidas anteriores ao corte
-- :team_id e :cutoff_date são bind parameters validados.
-- A ingestão normaliza jogos concluídos para status = 'final'.
SELECT g.source_game_id, g.game_date,
       CASE WHEN g.home_team_id = :team_id
            THEN g.home_score ELSE g.visitor_score END AS points_for,
       CASE WHEN g.home_team_id = :team_id
            THEN g.visitor_score ELSE g.home_score END AS points_against
FROM games g
WHERE g.status = 'final'
  AND g.game_date < :cutoff_date
  AND (g.home_team_id = :team_id OR g.visitor_team_id = :team_id)
ORDER BY g.game_date DESC, g.source_game_id DESC
LIMIT 10;
Para prever jogos históricos em dias com várias partidas, usar uma política consistente de fechamento por data, quando a
hora exata da disponibilização não é confiável. O algoritmo de features deve consumir a sequência de jogos anteriores,
não uma tabela de estatísticas de temporada já consolidada ao fim do ano.
D.3 Testes anti-leakage e sanidade de probabilidades
 pytest — testes contratuais ilustrativos
def test_future_result_does_not_change_pregame_features():
    games = make_tiny_fixture_with_future_game()
    before = build_features(games, game_id=10, as_of="2024-01-10")
    games = edit_score_after_cutoff(games, game_id=11, score=999)
    after = build_features(games, game_id=10, as_of="2024-01-10")
    assert before == after
def test_probability_contract(prediction_service):
    result = prediction_service.predict(home_id=1, away_id=2,
                                        as_of="2024-01-10")
    assert 0 <= result.p_home_win <= 1
    assert 0 <= result.p_away_win <= 1
    assert abs(result.p_home_win + result.p_away_win - 1) < 1e-8

contratos de testes que serão implementados no repositório. O objetivo é fixar o comportamento esperado.

Apêndice E. Glossário e decisões pendentes
 TERMO
DEFINIÇÃO OPERACIONAL
RAG
Recuperação de evidências relevantes adicionadas ao contexto do LLM na consulta.
LLM
Modelo de linguagem usado para síntese textual; não determina as probabilidades esportivas.
Embedding
Representação vetorial de trecho para busca por similaridade.

Variável explicativa pré-jogo usada no modelo supervisionado.

Modelo de referência que precisa ser comparado com candidatos mais complexos.

Avaliação retrospectiva com simulação fiel do que se sabia em cada corte.
Leakage
Contaminação com informação não disponível no instante em que a previsão deveria ser feita.
Calibração
Ajuste/verificação da correspondência entre probabilidades e frequências observadas.
Snapshot
Conjunto de dados ou recursos congelados e identificados por versão/hash.
as_of
Instante-limite do conhecimento utilizado em previsão, recuperação e auditoria.
Champion / challenger
Modelo em uso e candidato submetido a comparação experimental.

 • Partidas da NBA Cup e playoffs entram no recorte ou permanecem separadas?
